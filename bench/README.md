# Benchmarks

atago is measured the way a user or CI runs it, one process per call from start to exit, with [himorime](https://github.com/nao1215/himorime). himorime builds atago, runs each command in interleaved rounds, and reports latency, CPU time, peak RSS and, for the large spec, throughput in scenarios per second.

```console
$ go install github.com/nao1215/himorime@latest
$ make bench            # himorime run bench
$ make bench-compare    # himorime compare --against main bench
```

## Regression suite: himorime.yaml

`make bench-compare` checks main out into a temporary Git worktree, builds it and your working tree, and measures both in the same rounds, so a background job slows both revisions instead of one. `BASE=v0.22.0 make bench-compare` compares against another revision. `himorime run --filter 'run 1000' bench` measures one benchmark.

On a pull request, `.github/workflows/bench.yml` runs `himorime ci bench` the same way, with the base of the pull request as the base, on one runner. The job fails when a command is slower, uses more CPU time or more memory than the base beyond the tolerance in `himorime.yaml` with 95% confidence. The tolerance for memory is wide (50%) on purpose: atago spends memory where that saves time, such as its garbage collector target. A difference too close to call is reported as inconclusive and does not fail the job. The comparison is on the job summary page and the JSON report is kept as an artifact.

The specs are generated by `gen.sh` before measuring, so no fixture is added, and both revisions run the working tree's `gen.sh`. Every scenario runs `echo` without a shell and asserts its exit code and standard output, so the time is atago's own work, not the program under test. atago runs in the benchmark's own directory, with `HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME` and `TMPDIR` pointed into it.

| Benchmark | Commands | Measures |
|-----------|----------|----------|
| `version` | `atago version` | starting atago |
| `run 10` | `atago run --parallel 1` on a spec of 10 scenarios | a small suite, where start-up and loading the spec dominate; one at a time, because with the default concurrency the time of 10 scenarios varies too much from run to run to compare |
| `run 1000` | `atago run` and `atago run --parallel 1` on a spec of 1000 scenarios | loading the spec, a temporary directory and a process per scenario, the assertions and the report, with the default concurrency and one scenario at a time |
| `run error` | `atago run` on a path that does not exist | the error path, exit 3 |

Numbers from different machines are not comparable; compare revisions on one machine, as `make bench-compare` and CI do.
